# 四套方案的融合架构

## 结论

建议分两步合并：

1. 先通过统一客户端把四套方案变成可替换引擎，建立一致的输入、运行、日志和结果协议。
2. 再从稳定性最高的模块开始做能力级融合，而不是直接复制四套 ReAct 循环。

当前目录已经完成第一步。

## 各方案最值得保留的能力

### Mamba Agent：输入与工具底座

优先复用其 ETL router、schema normalize、单位处理、文档/视频/SQLite 工具、原生 tool calling 和 tracing。它最适合成为统一流水线的“数据平面”。

### LangGraph：显式编排

复用状态图、question analyzer、ambiguity analyzer、data inspector、process validator、answer validator，以及视频关键帧和 ASR 预处理。它最适合成为“控制平面”。

### Kobushi：分阶段推理

把 `PLAN → EXPLORE → ANSWER → VERIFY` 作为统一状态机的主干，并保留 source router、SQL guard、projection pruner 等经过大量实验筛选的策略。它最适合提供“推理策略”。

### Memory ReAct：重试与长期经验

复用 difficulty-aware budget、self-consistency、cross-run vote、task shape、error patterns 和 learnings recorder。它最适合提供“可靠性与记忆层”。

## 推荐的目标流水线

```text
标准任务
   │
   ▼
Mamba ETL / Schema Normalization
   │
   ▼
LangGraph State + Modality Router
   │
   ├── PLAN
   ├── EXPLORE ── Mamba tools / video / ASR
   ├── ANSWER
   └── VERIFY ── LangGraph validators / SQL guards
   │
   ▼
Risk Gate
   ├── 低风险：直接输出
   └── 高风险：Memory self-consistency + cross-run vote
   │
   ▼
统一 prediction.csv + trace + provenance
```

## 统一接口建议

能力级融合时，先固定下面五个协议：

```python
class TaskSource(Protocol):
    def load(self, task_id: str) -> Task: ...

class ContextInspector(Protocol):
    def inspect(self, task: Task) -> ContextManifest: ...

class ToolExecutor(Protocol):
    def definitions(self) -> list[ToolDefinition]: ...
    def execute(self, call: ToolCall, scope: TaskScope) -> ToolResult: ...

class AgentEngine(Protocol):
    def run(self, task: Task, services: Services) -> CandidateAnswer: ...

class AnswerPolicy(Protocol):
    def validate(self, candidate: CandidateAnswer) -> ValidationReport: ...
    def select(self, candidates: list[CandidateAnswer]) -> FinalAnswer: ...
```

不要让融合层直接依赖某个仓库内部的 `AppConfig`、消息类或工具注册表；通过薄适配器完成转换。

## 路由与成本控制

不建议所有任务默认四引擎并跑。目标策略可以是：

| 任务信号 | 默认路径 | 升级条件 |
| --- | --- | --- |
| 单表 CSV / 简单聚合 | Mamba ETL + 单次 ReAct | 校验失败或答案形状不稳 |
| 多文件 / 多表关系 | LangGraph inspector + phased ReAct | 连接关系置信度低 |
| 视频 / 音频 | LangGraph/Kobushi ASR 路径 | ASR 低置信度或视觉证据冲突 |
| hard / extreme | phased ReAct | 默认触发二次验证 |
| 高风险答案 | 任意主路径 | Memory 多次采样与投票 |

这样可保留四套方案的互补优势，同时避免四倍模型成本。

## 实施顺序

1. 用当前客户端跑同一批公开任务，收集四套引擎的成功率、耗时、失败类型和答案差异。
2. 抽取统一的 `Task`、`AnswerTable`、`TraceEvent` 数据模型。
3. 先替换工具层：让 LangGraph/Kobushi 调用 Mamba 的 ETL 与工具协议。
4. 再迁移验证器和 SQL guard，确保每一步有可比较的回归结果。
5. 最后引入 Memory 的风险门控、重试和投票；避免一开始就无条件多跑。
