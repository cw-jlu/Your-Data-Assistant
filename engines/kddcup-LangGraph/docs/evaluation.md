# KDD Cup 2026 Data Agents 评测结果与开发复盘

> 文档状态：Current
> 最近核对：2026-07-21
> 官方结果：Phase 2 Leaderboard Track 最终第 7 名
> 适用范围：项目复盘、简历撰写和面试准备

本文档以**线上最终榜成绩**作为项目的主要结果，以公开 demo 的本地评测作为开发诊断证据。两者的数据、运行环境和评分参数不同，不能直接比较，也不能把本地 Proxy Score 写成官方成绩。

## 1. 技术摘要

团队 `idmg123`（Team ID `1513`）在 KDD Cup 2026 Data Agents **Phase 2 Leaderboard Track** 中取得线上最终第 **7** 名：

|        Rank |        Team ID | Team Name         |          A Score |          B Score |      Final Score |
| ----------: | -------------: | ----------------- | ---------------: | ---------------: | ---------------: |
| **7** | **1513** | **idmg123** | **0.5240** | **0.5775** | **0.5695** |

这是本项目最重要、最适合写入简历的结果。官方当前 [Leaderboard 页面](https://dataagent.top/leaderboard) 可核验 Team ID `1513` 的 A Score 为 `0.5240`、A-board 排名为第 7；B Score、Final Score 和最终名次来自比赛最终榜截图。

从截图数值可以复算：

```text
0.15 × 0.5240 + 0.85 × 0.5775 = 0.569475 ≈ 0.5695
```

因此，`Final Score` 是 A/B Score 的加权结果，而不是二者的简单平均。`0.5695` 也不应表述为“56.95% 准确率”；更准确的说法是“官方 Final Score 0.5695”。

本地公开集评测提供了另一组互补证据：最终完整运行对 60/60 任务生成了结果，严格完全正确 35 题，Mean Recall 为 0.7750，项目内部 `lambda=0.1` 的 Proxy Score 为 0.7625。这些数字用于解释系统能力与开发过程，**不是官方隐藏集成绩**。

## 2. 线上第 7 名证明了什么

官方成绩表明，这套系统在统一模型、统一资源限制和隐藏测试集下，具备有竞争力的端到端数据分析能力。它验证的是整套系统的综合效果，包括：

- 对 CSV、JSON、SQLite、文档、图像和视频等异构数据的识别与处理；
- 根据问题动态选择 SQL/Python、文档检索、视觉读取等工具；
- 将多步中间结果合并为满足格式要求的 `prediction.csv`；
- 在隐藏数据分布、统一容器环境和总运行时限下保持可执行性。

需要注意，排行榜只给出系统级结果，不能单独证明某个模块带来了多少提升。若要说明 Catalog、答案校验、长文档处理或 Video Agent 的作用，应使用 trace 和案例解释其机制，不应把相邻版本的分差直接写成单模块因果增益。

## 3. 官方评分口径

官方评测采用列级内容匹配。对每个任务，评分器会规范化单元格，将每列的值排序后形成列签名，再按签名匹配 prediction 和 gold。列名和行顺序通常不参与普通列匹配，相同内容的重复列按出现次数匹配。

记：

- `G`：Gold Columns，标准答案列数；
- `P`：Predicted Columns，预测列数；
- `M`：成功匹配的列数；
- `E`：未匹配的冗余预测列数。

单题核心指标为：

```text
Recall = M / G
Redundancy Rate = E / P
Score = max(Recall - lambda × Redundancy Rate, 0)
```

这个设计首先奖励对 gold 列的完整覆盖，同时对多余列施加轻量惩罚。官方规则还包括空值、数字、日期时间和字符串的规范化；详细要求以 [官方技术规范](https://dataagent.top/rules) 的最新版本为准。

### 3.1 三个容易混淆的概念

| 名称                  | 判定                                      | 可以说明什么                                  |
| --------------------- | ----------------------------------------- | --------------------------------------------- |
| 运行成功              | Agent 正常结束并写出结果                  | 工程链路可执行，不代表答案正确                |
| 完全覆盖 / Full Cover | `Recall = 1`                            | gold 列全部找到，但可能存在冗余列             |
| 严格完全正确          | `Recall = 1` 且 `Redundancy Rate = 0` | gold 全覆盖且没有多余列，适合用于本地结果汇报 |

因此，“60/60 产出”不能写成“60/60 正确”，“完全覆盖”也不能直接等同于满分。

## 4. 官方成绩与本地评测必须分开解释

| 维度     | 官方线上评测                     | 本地公开集代理评测                      |
| -------- | -------------------------------- | --------------------------------------- |
| 数据     | 官方隐藏 A/B board               | 仓库公开 demo 的`gold.csv`            |
| 环境     | 官方统一容器、模型、资源和时限   | 本机服务、代码和运行配置                |
| 主要用途 | 产生官方分数与排名               | 开发诊断、回归比较和失败分析            |
| 惩罚系数 | 官方预设，以实际评测配置为准     | 项目内部固定主口径`lambda=0.1`        |
| 可用表述 | “最终第 7，Final Score 0.5695” | “60 题公开集本地 Proxy@0.1 为 0.7625” |

即使两者使用相似的列匹配公式，结果也不可互换。公开集规模更小，且在开发中被重复使用；本地模型服务、并发、缓存和超时策略也可能与官方环境不同。

## 6. Trace 能支撑的工程结论

在本地保存运行峰值的 60 个任务中：

- 49 题调用查询工具；
- 29 题读取图像；
- 21 题读取文档；
- 17 题调用结构化文档抽取。

这组记录可以支撑“系统根据任务上下文动态编排结构化查询、文档处理和视觉工具”的描述。trace 可能同时记录请求侧和执行侧事件，因此工具记录数不应解释为独立网络请求次数。

更适合面试展开的两个方向是：

1. **成功路径**：系统先识别数据模态，再选择查询或读取工具，保留证据并生成结构化答案；适合展示规划、工具调用和答案校验的完整链路。
2. **失败路径**：长文档或复杂任务可能消耗大量 Token 后超时，或者虽然生成了列但列内容无法匹配 gold；适合讨论预算控制、早停、降级输出和冗余列约束。

## 7. 结论边界与不确定性

以下限制会影响对本地实验的解释：

- 公开 demo 被多次用于开发，可能存在针对固定题集的调优偏差；
- 历史运行没有完整保存 commit、配置快照和数据 hash，无法严格复现实验环境；
- 历史任务难度均记录为 `unknown`，不能给出 Easy/Medium/Hard/Extreme 分项结论；
- baseline 和后期运行并非单变量控制实验，不能声称单个组件具有确定的因果增益；
- 本地 `lambda=0.1` 是项目内部代理口径，不等于官方隐藏评测参数；
- 最终 B Score、Final Score 和最终排名目前以用户提供的最终榜截图为直接证据，建议将原图长期归档，避免依赖临时文件。
